# Решение: Telegram Message Dispatcher

Статус: **accepted v2** для D2–D10; D1 (Telegram-слой) открыт. Ответы владельца: [../telegram-core/01-request.md](../telegram-core/01-request.md).

Итог ответов: Premium есть; закрепление диалога и ручное переназначение — решение владельца (D2 accepted); операторы — отдельные аккаунты, выбирают шаблон или пишут сами; рабочий чат есть, заявки приходят пачками по ~50 со ссылкой на клиента; хостинг — бесплатный сторонний, без домена (long polling); классификация через Claude разрешена; репозиторий — skill01; шаблоны позже.

**D1 — сценарий подтверждён владельцем (2026-10-12): Б.** Цитата: «Сообщения приходят в общий чат, где по очереди его берут нужные аккаунты. 1 и 2, 1 написал сообщение по шаблону, вышел и поставил реакцию. 2 пошёл в общий чат увидел первое сообщение без реакции и написал ему по шаблону». Значит, аккаунт оператора пишет клиенту **первым** по ссылке из общего чата; реакция — ручная отметка «взято». Business-бот для отправки не подходит (`can_reply` только в чатах с входящим за 24 ч).

Решение по слоям:
- **Приём:** бот (aiogram) в общем чате читает каждую заявку → `ingest_message(source='work_chat')`, клиент — по ссылке. Атомарное назначение в БД заменяет реакции (две учётки не возьмут одну заявку; один клиент из разных пачек остаётся за тем же оператором). Реакцию бот может ставить для наглядности, но источник истины — БД.
- **Отправка, вариант Б1 (рекомендован для старта):** бот присылает оператору карточку: ссылка, текст шаблона, кнопки «Отправил» / «Не получилось» / «На проверку». Оператор пишет из своего приложения. Сессии аккаунтов на сервере не хранятся; риск блокировки из-за автоматизации отсутствует.
- **Отправка, вариант Б2 (по отдельному решению владельца):** Telethon на аккаунтах операторов, отправка после подтверждения оператором. Жёсткий суточный и почасовой лимит на аккаунт; PEER_FLOOD/ограничение → аккаунт на паузе, заявки на ручную проверку; **без** ротации аккаунтов, имитации человека и иных обходов (принцип 6 ТЗ). Первые сообщения незнакомым людям пачками — именно то, что антиспам Telegram ограничивает.
- Открыто: формат ссылки в заявке; кто публикует пачки (человек пересылает или бот/парсер — бот не видит сообщения других ботов в группе); выбор Б1/Б2; хостинг.
Автор: оркестратор make-feature, Claude Code (облачная сессия), 2026-10-12.
Входы: [01-request.md](01-request.md), [00-index.md](00-index.md).

## Основания (факты S*)

Проверено командами и документацией 2026-10-12.

**Среда**
- S1. Контейнер: Ubuntu 24.04.5, x86_64, Python 3.13.16, uv, git 2.43, Node 22, Claude Code 2.1.296.
- S2. Есть PostgreSQL 16.15 (кластер остановлен, можно запустить локально для тестов) и Redis 7.0.15. Docker CLI установлен, но daemon не запущен, поэтому testcontainers здесь недоступен.
- S3. Контейнер облачный и временный: он удаляется после простоя. Для production он не подходит, и Telegram-сессии здесь хранить нельзя. Нужен постоянный сервер.
- S4. MCP: подключены только плагины design/marketing, и они к задаче не относятся. Работа с файлами и git встроена в Claude Code, поэтому Filesystem MCP не нужен. GitHub доступен через встроенные MCP-инструменты в пределах репозитория `mrasskazov690-cloud/skill01`.
- S5. Репозиторий `skill01` **публичный** и почти пустой.
- S6. TCP до DC Telegram (149.154.167.50:443) открыт. Сам протокол MTProto не проверялся.

**Telegram**
- S7. Последняя версия Bot API — 10.3 от 2026-08-24 ([core.telegram.org/bots/api](https://core.telegram.org/bots/api)). Режим Business даёт обновления `business_connection` и `business_message`. В `BusinessBotRights.can_reply` сказано: «True, if the bot can send and edit messages in the private chats that had incoming messages in the last 24 hours». Значит, от имени основного аккаунта бот может отвечать только в окне 24 часа после входящего сообщения.
- S8. Нужен ли Telegram Premium для подключения бизнес-бота — **неизвестно**. Раньше Premium требовался. Один вендор (SendPulse) пишет, что с 2026-05-08 это не так, но официального подтверждения нет. Проверяется в приложении: Настройки → Telegram Business → Чат-боты.
- S9. Условия API ([core.telegram.org/api/terms](https://core.telegram.org/api/terms)): у приложения должен быть свой `api_id`. Запрещены действия «on behalf of the user without the user's knowledge and consent». Запрещено использовать данные Telegram для обучения моделей. При нарушении Telegram присылает уведомление и закрывает доступ к API через 10 дней.
- S10. На странице ошибок описан FLOOD_WAIT_X: нужно ждать X секунд. PEER_FLOOD там не описан, поэтому считаем его остановкой отправки для аккаунта, без автоматического повтора.

## Варианты Telegram-слоя

Всё упирается в вопрос: от чьего имени клиент получает ответ.

| Вариант | Как работает | Плюсы | Цена и риск | Вердикт |
|---|---|---|---|---|
| A. Бизнес-бот | Основной аккаунт подключает нашего бота как чат-бота Telegram Business. Входящие приходят как `business_message`. Ответ уходит от имени основного аккаунта через `business_connection_id`. Операторы работают в рабочем чате через кнопки того же бота | Официальный Bot API; на сервере нет пользовательских сессий; клиент общается с одним и тем же аккаунтом; минимум риска блокировки | Окно 24 часа (S7); возможно, нужен Premium (S8); видны только разрешённые чаты | **Рекомендован** |
| B. MTProto на основном аккаунте | Telethon под основным аккаунтом получает сообщения и отвечает | Полный доступ к истории, нет окна 24 часа | Сессия даёт полный доступ к аккаунту; автоматизация личного аккаунта находится в серой зоне правил; нужен свой `api_id` (S9) | Резерв, если A недоступен |
| C. MTProto на аккаунтах операторов | Оператор пишет клиенту со своего аккаунта | Ответ приходит от конкретного человека | Клиент писал на основной аккаунт, и сообщение от незнакомого аккаунта — это холодный контакт: высокий риск PEER_FLOOD и жалоб на спам. Нужен username клиента. По 2–3 сессии на каждого оператора | Не рекомендую, решать владельцу |

Слой Telegram в любом варианте будет за интерфейсом `TelegramAccount` (получение, диалог, отправка, проверка связи). Поэтому A → B заменяется без переписывания бизнес-логики.

## Предварительные решения D*

- **D1. Telegram:** вариант A (aiogram 3.31). Telethon 1.45 — только как реализация того же интерфейса, если владелец выберет B или C.
- **D2. Единица распределения — диалог.** В аренде клиент обычно присылает серию сообщений, поэтому диалог закрепляется за оператором, новые сообщения наследуют назначение, переназначение делается явно. Round-robin идёт по операторам, у которых `enabled`, открыта смена и есть запас по нагрузке.
- **D3. Хранение и очередь — PostgreSQL 16.** Очередь — это таблица и `SELECT … FOR UPDATE SKIP LOCKED`. Для отправок — outbox. Дедупликация входящих — `UNIQUE(account_id, chat_id, tg_message_id)` и `UNIQUE(update_id)`. Миграции — Alembic, доступ — SQLAlchemy 2.1 async + asyncpg.
- **D4. Redis не нужен.** 500 сообщений в день — это примерно 0,006 в секунду. Блокировки строк PostgreSQL закрывают C3. Пересмотрим, если понадобится несколько инстансов с общим rate-limit.
- **D5. Отправка.** Одна строка outbox на ответ (ключ — заявка и версия шаблона). Статусы: `queued → sending → sent | uncertain | failed`. Тайм-аут даёт `uncertain`, автоматического повтора нет, решает оператор (C7). У Bot API нет ключа идемпотентности. В MTProto есть `random_id` с серверной дедупликацией — это гипотеза, проверим на этапе 4, если выберем B или C.
- **D6. Шаблоны.** Сначала правила (ключевые слова и шаблоны). Потом, если владелец разрешит (Q6), Claude через Anthropic API со структурным ответом `{intent, template_id, confidence, fields}`. При низкой уверенности — `awaiting_review`. Текст шаблона не меняется, кроме явно разрешённых полей.
- **D7. MCP.** Свой сервер на `mcp` 2.3.0 (`MCPServer`, stdio). Инструменты вызывают сервисный слой backend и не исполняют сырой SQL. `send_approved_reply` отправляет только утверждённый шаблон. Произвольный текст в MCP не отправляется: ручную отправку делает оператор через рабочий чат.
- **D8. Конфигурация и логи.** pydantic-settings и `.env` (в Git только `.env.example`). Логи — structlog в JSON, без полного текста клиента: в логах только ID.
- **D9. Тесты.** pytest и pytest-asyncio на реальном локальном PostgreSQL, отдельно тест конкурентного захвата. Telegram в unit-тестах подменяется фейковым адаптером; интеграционные тесты — только с тестовым чатом.
- **D10. Production** — постоянный Linux VPS (systemd или docker compose), не облачный контейнер (S3). Резервные копии — `pg_dump` по расписанию и проверка восстановления.

Главный способ провала — отправка дубля или неверного шаблона клиенту. Защита: outbox, `uncertain` без повтора, ручная проверка при низкой уверенности, пилот на малом потоке (этап 13).

## Вопросы к владельцу (блокируют Telegram-слой)

- **Q1.** Основной аккаунт — обычный личный аккаунт (не бот)? Можно ли подключить ему бизнес-бота: виден ли пункт «Telegram Business → Чат-боты», есть ли Premium?
- **Q2.** От чьего имени клиент должен получать ответ: основного аккаунта (A/B) или аккаунтов операторов (C)?
- **Q3.** Операторы — живые люди со своими аккаунтами? Они подтверждают и выбирают шаблоны кнопками или пишут клиенту вручную?

- **Q6.** Можно ли передавать тексты клиентов в Anthropic API для классификации или только правила? В какой юрисдикции персональные данные (например, 152-ФЗ требует хранить их на серверах в РФ) и сколько их хранить?
