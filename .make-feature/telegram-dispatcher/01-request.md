ТЕХНИЧЕСКОЕ ЗАДАНИЕ: TELEGRAM MESSAGE DISPATCHER

Создать систему автоматизации обработки входящих заявок в Telegram с использованием Claude Code, MCP, Python, PostgreSQL и при необходимости Redis.

ЦЕЛЬ
У меня есть один основной Telegram-аккаунт, на который поступают входящие сообщения от потенциальных клиентов, и два-три аккаунта операторов, через которые обрабатываются заявки. Ожидаемый объём — до 500 входящих сообщений в день. Тематика заявок — аренда жилья и связанные услуги. Нужно получать сообщения, сохранять их, передавать в общий рабочий чат, распределять между операторами, подбирать утверждённые шаблоны ответов, отправлять ответы и отслеживать результат.

ВАЖНЫЕ ПРИНЦИПЫ
1. Не считать, что я новичок. Не объяснять основы API, ключей, кода и коннекторов без необходимости.
2. Не пытаться создать всё одним огромным фрагментом кода. Сначала изучить среду и доступные инструменты, затем реализовывать проект по этапам.
3. Не предполагать заранее, что существуют нужные MCP-коннекторы или что они поддерживают конкретные операции. Проверять актуальную документацию, версии, лицензии и ограничения.
4. Claude Code используется для разработки и сопровождения проекта. В рабочей системе критическая логика должна исполняться обычным backend-кодом, а не зависеть от того, открыт ли Claude.
5. Для обычных Telegram-аккаунтов изучить MTProto и совместимые клиентские библиотеки. Для ботов использовать Bot API, если это соответствует фактическому типу аккаунта и нужным возможностям. Не предполагать, что Bot API способен управлять обычными пользовательскими аккаунтами.
6. Соблюдать условия Telegram, ограничения API, правила платформы и требования к защите персональных данных. Не реализовывать обход лимитов, антиспам-механизмов или блокировок. Не использовать чужие аккаунты без разрешения.
7. Все отправки должны контролироваться кодом, иметь журнал событий и защищаться от случайных повторов. Не считать сообщение отправленным без подтверждения API.

ЦЕЛЕВАЯ АРХИТЕКТУРА
Входящие Telegram-сообщения → Telegram Adapter → Message Handler → PostgreSQL → Queue/Dispatcher → назначенный оператор → выбор утверждённого шаблона или ручная обработка → Telegram API → подтверждение отправки → обновление статуса → журнал и рабочий чат.

Claude может управлять системой через собственный MCP-сервер и помогать с классификацией сообщений, выбором шаблонов, диагностикой, статистикой и администрированием. Постоянная обработка сообщений не должна зависеть от непрерывного участия Claude.

ТЕХНОЛОГИЧЕСКИЙ СТЕК
Основной язык — Python, если исследование доступных библиотек не выявит веских причин выбрать другой вариант. Изучить Telegram-клиент для MTProto, официальный Bot API при необходимости, PostgreSQL, Redis при обоснованной необходимости, библиотеку MCP для Python, конфигурацию через переменные окружения, миграции базы данных, логирование и автоматические тесты.

MCP И КОННЕКТОРЫ
Исследовать и при необходимости настроить:
- Filesystem MCP для работы Claude Code с файлами проекта, если аналогичная возможность не встроена в используемую среду.
- Git/GitHub-инструменты для версионирования, если они полезны и доступны.
- Собственный Telegram MCP server, который предоставит безопасные инструменты управления сообщениями, очередью, шаблонами и статистикой.
- Подключение к PostgreSQL и Redis выполнять преимущественно из backend. Не давать модели прямой доступ на произвольное изменение производственных данных, если для задачи достаточно ограниченных функций backend.

Перед установкой сторонних MCP-серверов проверить их репозитории, происхождение, разрешения, поддержку нужных методов и риски хранения сессий. Не считать сторонний MCP обязательным, если безопаснее написать собственный.

TELEGRAM API
Если используются обычные пользовательские аккаунты, изучить MTProto, получение api_id/api_hash, безопасную авторизацию и хранение отдельной сессии каждого разрешённого аккаунта. Если используются боты, проверить возможности Bot API. Сначала реализовать и протестировать один входящий аккаунт и один разрешённый аккаунт отправки, затем добавить остальные.

Telegram-слой должен предоставлять абстракцию аккаунта и операции получения новых сообщений, получения сведений о диалоге, отправки ответа, проверки соединения и обработки ошибок. Разделить реализацию Telegram API и бизнес-логику, чтобы можно было менять библиотеку без переписывания всей системы.

ОСНОВНЫЕ СУЩНОСТИ БАЗЫ ДАННЫХ
1. accounts: внутренний ID, идентификатор Telegram, тип аккаунта, имя, состояние, признак включения, время последнего назначения, диагностические сведения.
2. conversations: ID диалога, идентификатор исходного чата, клиент, назначенный оператор, статус и время последней активности.
3. messages: внутренний ID, идентификатор исходного сообщения Telegram, диалог, текст и метаданные, статус, назначенный оператор, выбранный шаблон, время получения, назначения и отправки.
4. assignments: история назначений заявок операторам.
5. templates: ID, название, тип обращения, текст, язык, условия применения, активность и версия.
6. settings: безопасно хранимые настройки маршрутизации и обработки, не секретные ключи.
7. audit_log: история действий, назначений, отправок, ошибок и административных изменений без лишнего копирования личных данных.

У каждого входящего сообщения должен быть стабильный внутренний ID. Идентификаторы Telegram сохраняются отдельно. Предусмотреть уникальные ограничения, чтобы повторное получение одного update не создавало дубликаты.

ОЧЕРЕДЬ И РАСПРЕДЕЛЕНИЕ
Реализовать диспетчер, который назначает каждое подходящее сообщение одному разрешённому оператору. Поддержать round-robin между включёнными аккаунтами, а также возможность учитывать доступность и текущую нагрузку, если это действительно требуется.

Назначение должно выполняться атомарно: два процесса не должны одновременно захватить одну заявку. Можно использовать транзакции PostgreSQL и блокировки строк; Redis применять только при наличии обоснованной необходимости. Не считать аккаунт свободным исключительно на основании локального флага без проверки его состояния.

Предусмотреть состояния pending, assigned, processing, answered, failed, cancelled и при необходимости awaiting_review. Переходы между статусами должны проверяться. Для зависших задач предусмотреть безопасное восстановление и повторную обработку.

Не смешивать распределение отдельных сообщений с распределением целых диалогов. Исследовать, какой режим лучше подходит для аренды жилья. Если клиент присылает несколько последовательных сообщений, желательно сохранять контекст диалога и не назначать ответы разным операторам без необходимости. Поддержать закрепление диалога за оператором и явное переназначение.

ШАБЛОНЫ ОТВЕТОВ
Создать механизм хранения и поиска утверждённых шаблонов. Примеры категорий: вопрос об актуальности, стоимость, месячная аренда, даты, количество гостей, просмотр объекта, запрос вариантов, уточнение бюджета и нестандартное обращение.

Правила и классификатор могут определять категорию сообщения. При необходимости использовать Claude для классификации и извлечения параметров. Предпочтительно получать структурированный результат с template_id, intent, confidence и необходимыми полями, а не произвольный текст.

Если найден подходящий утверждённый шаблон, отправлять его без изменения, если только правила явно не разрешают подстановку полей. Не придумывать цены, доступность жилья, адреса и условия бронирования. Если уверенность классификации низкая, контекста недостаточно или запрос нестандартный, переводить обращение на ручную проверку.

ОБЩИЙ РАБОЧИЙ ЧАТ
Исследовать безопасный способ интеграции с рабочим Telegram-чатом. В чат можно отправлять уведомления о новых заявках, назначениях, статусах, ошибках и статистике. Уведомление должно содержать внутренний ID, краткий текст сообщения, назначенного оператора и текущий статус с учётом конфиденциальности.

Рассмотреть команды или кнопки для просмотра заявки, ручного назначения, переназначения, подтверждения ответа, пропуска и выбора шаблона. Проверять права пользователей рабочего чата. Не полагаться на текст пересланного сообщения как на единственный источник состояния: все действия должны ссылаться на внутренний ID и проверяться в базе данных.

ОТПРАВКА И НАДЁЖНОСТЬ
Перед отправкой проверить, что заявка назначена нужному оператору, диалог существует, ответ разрешён и заявка не была обработана ранее. Записывать попытку отправки и результат. При сетевом тайм-ауте не считать, что сообщение точно не отправлено: сначала проверить возможность определить результат, чтобы не отправить дубликат.

Использовать идемпотентную обработку входящих updates, транзакции базы данных, ограниченные повторы, обработку flood-wait и других предусмотренных API ошибок, журналирование и метрики. Не пытаться обходить ограничения отправки. Не обещать exactly-once доставку, если API её не гарантирует; проектировать систему с контролем неопределённого результата и предотвращением максимально возможного числа дублей.

БЕЗОПАСНОСТЬ
Секреты, api_hash, токены, пароли и строки подключения хранить в переменных окружения или подходящем менеджере секретов. Не записывать их в Git, журналы, промпты и обычные отчёты. Telegram session-файлы считать секретами и ограничить к ним доступ. Создать .env.example без действующих секретов и корректный .gitignore.

Добавить авторизацию для административных операций, разграничение прав, безопасную обработку пользовательского текста, резервное копирование и инструкцию восстановления. Не запускать произвольный код, полученный из сообщений клиентов. В MCP ограничить операции необходимыми функциями и не предоставлять модели лишние привилегии.

Этап 2. Составить краткий технический план с конкретными библиотеками и обоснованием выбора. Проверить официальную документацию и совместимость версий. Выяснить тип входящего аккаунта и тип аккаунтов отправки.

Этап 3. Подготовить репозиторий, конфигурацию, структуру, зависимости, тестовую среду и безопасную работу с секретами.

Этап 4. Реализовать Telegram Adapter для одного разрешённого аккаунта. Проверить авторизацию, получение новых сообщений, получение контекста и тестовую отправку в разрешённый тестовый диалог.

Этап 5. Добавить PostgreSQL, модели, миграции, сохранение сообщений, уникальные ограничения и идемпотентную обработку входящих updates.

Этап 6. Реализовать очередь, атомарное назначение, статусы, round-robin, обработку ошибок и восстановление незавершённых задач. Написать тесты конкурентного назначения.

Этап 7. Подключить остальные разрешённые аккаунты. Проверить авторизацию, состояние соединений, ограничения API и корректность маршрутизации.

Этап 8. Добавить хранилище шаблонов, правила классификации, проверку уверенности и ручную обработку неоднозначных сообщений.

Этап 9. Реализовать собственный MCP-сервер и подключить его к Claude Code. Проверить каждую функцию по отдельности. MCP используется для управления и диагностики, а постоянная автоматическая обработка выполняется backend-сервисом.

Этап 10. Подключить общий рабочий чат и безопасные команды управления. Проверить права доступа и связь каждого уведомления с записью в базе.

Этап 11. Добавить журналирование, статистику, мониторинг, health checks, резервное копирование и инструкции восстановления.

Этап 12. Провести интеграционные тесты, тесты отказов, повторных updates, одновременного поступления заявок, временной недоступности аккаунтов, сетевых тайм-аутов и неоднозначных результатов отправки.

Этап 13. Провести ограниченный пилот на небольшом потоке реальных разрешённых обращений. Проверить отсутствие дубликатов, правильность шаблонов, распределение и корректность статусов. Только после проверки включать полную автоматизацию.

КРИТЕРИИ ГОТОВНОСТИ
- Входящие сообщения надёжно сохраняются и не создают дубликаты при повторном получении.
- Каждая заявка имеет внутренний ID, историю событий и понятный статус.
- Одну заявку нельзя одновременно назначить двум операторам.
- Распределение работает по выбранному алгоритму и учитывает закрепление диалогов.
- Шаблоны хранятся централизованно и выбираются предсказуемо.
- Неоднозначные случаи можно отправить на ручную проверку.
- Успешная отправка подтверждается API, а неопределённые результаты не приводят к слепому повтору.
- MCP предоставляет ограниченные и проверяемые инструменты управления.
- Секреты и Telegram-сессии защищены.
- Есть тесты, логи, инструкции запуска, диагностики и восстановления.
- Система рассчитана на целевой поток до 500 входящих сообщений в день без необходимости держать открытым Claude.

ПРАВИЛА РАБОТЫ CLAUDE CODE
Работай итеративно. Сначала изучи среду и документацию, затем предложи стек и план. После согласования реализуй этапы последовательно. Для каждого этапа создавай код, тесты и инструкции; запускай тесты и исправляй ошибки до перехода к следующему этапу.

Не заявляй, что функция готова, пока она не реализована и не проверена. Не выдумывай существование MCP-инструментов, возможностей API, переменных окружения или результатов тестирования. Если необходимы мои действия — авторизация, получение ключа, выбор аккаунта, создание бота или подтверждение отправки — остановись на этом шаге и дай точную инструкцию.

Не раскрывай секреты в выводе. Не отправляй реальные сообщения клиентам и не запускай производственную автоматизацию без моего явного разрешения. Все потенциально опасные действия сначала проверяй на тестовых данных.
